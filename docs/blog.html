What breaks when agents talk
to each other

A multi-agent platform where you draw a graph of AI agents, give them tools, and chat with any of them. This is the design — and, more usefully, the bugs that only appear once agents start calling each other.

Build notes/ Multi-agent orchestration/ ~12 min read
The premise

Three requirements that shaped everything

Most "multi-agent" demos are a single agent with a fancy prompt. I wanted the real thing: a canvas where you create agents, connect them, give each one tools, and then talk to one of them — and it consults the others to answer you.

RequirementWhat it means in practice
VisualDrag out an agent, drag a line to another. Done.
ExplainableSee which agents were consulted, which tools ran, and why they were chosen.
ForgetfulEverything — agents, documents, API keys — is deleted after 48 hours.

That third one shaped the architecture more than anything else.

Part 1 — The pattern problem

What does a connection actually mean?

When agent A is connected to agent B, what happens at run time? There are several established answers — sequential pipeline, supervisor routing, conditional branching, parallel fan-out. I started with supervisor, implemented as agent-as-tool: each connected agent becomes a tool on the agent you're chatting with.

This is elegant. The model already knows how to choose tools, so it already knows how to choose agents. Routing comes free from a capability the model already has.

It worked on the first try. Then a user tried it and reported that it didn't work at all.

Part 2 — The bug that was a design flaw

The graph was right. My model of it was wrong.

"I connect two or three agents, I ask the 3rd agent one question, it's not communicating to the other agents for the answers."

My first instinct was that delegation tools weren't being bound. They were. So I wrote the smallest test that reproduced the user's setup — three agents, arrows pointing toward the final one:

There it is. My query followed outgoing edges. The user had drawn arrows pointing into their final agent — because that's the natural way to draw "these two feed the answerer." Their final agent had nothing to consult, so it answered alone, silently.

The call

I could have documented "draw your arrows this way." That would have been wrong. When users consistently draw something one way, the software is holding the wrong model. A connection stopped being directional: it now means "these two can talk."

Which immediately created a better question

Making edges undirected fixed the confusion and exposed a bigger gap. The user came back sharper: is this actually doing sequential, conditional, and the other orchestration patterns?

No. It was doing exactly one pattern and calling it orchestration. Worse, a condition_expr column had existed on every connection since the first commit — stored, returned by the API, editable in the UI, and never evaluated by anything. A field that looks like a feature and does nothing is worse than a missing feature.

The fix was a per-agent mode, with one rule that keeps it all coherent:

The invariant

In every mode except supervisor, the agent you chat with writes the final answer. The mode only decides how its connected agents contribute first. That single rule is what lets arrow direction stay irrelevant: the graph describes capability, the mode describes procedure.

ModeBehaviour
supervisorThe model is handed ask_B, ask_C as tools and picks. Flexible, not repeatable.
sequentialB runs, then C runs seeing what B said, then A composes. Deterministic.
parallelB and C run at once, then A merges. Fastest for independent questions.
conditionalOnly agents whose condition matches run, then A composes.

Conditional routing is one classification call covering every edge, not one per edge. And it fails open: if the model returns prose instead of JSON, every conditional agent contributes. Slower and more expensive — but a routing failure should never leave the user with no answer. That single decision is the difference between a flaky feature and a trustworthy one.

Part 4 — The one worth reading

A bug that had been there the whole time

I was writing a regression test that built an agent with a custom HTTP tool attached — something no test had done before. It blew up:

The code that built a tool's argument schema from stored JSON:

name: (type, FieldInfo) is create_model's signature. Passing it to type() creates plain class attributes with no annotations, which Pydantic v2 rejects outright.

Why it mattered more than it looked

get_agent_tools had no error handling, so the exception propagated up through graph construction and killed the entire agent. Attach a custom tool, and that agent stops answering — with an error pointing at Pydantic internals, nowhere near the cause.

None of these throw. They all silently produce a wrong answer, which is the worst failure mode a tool can have.

Part 5 — Observability

"The AI got it wrong" is not a debuggable statement

By now the system could answer by consulting three agents and running five tools. The naive approach to tracing is to instrument the orchestrator by hand — log before the model call, after the tool call. That falls apart immediately, because a delegated agent runs its own graph; you'd have to thread trace state through every call.

The better answer was already in LangChain: callbacks propagate down automatically.

One handler attached at the top captures everything beneath it, including inside sub-agents, in the correct order. To know which agent produced an event, every compiled graph is stamped with its own identity — and a delegated agent overrides the stamp for its subtree, so attribution falls out for free. That's the timeline at the top of this page.

Part 6 — Streaming

One async trap worth knowing

Two sources merge into one ordered stream: LangGraph's event iterator, and a queue that delegate tools push into. My first version leaked events:

shield protects the inner task from cancellation, so on timeout the queue.get() stays pending, eventually takes an item, and drops it on the floor. The fix is to own exactly one getter and cancel it only when it has not completed.

There's a second subtlety. Delegated agents run their own models, whose token events propagate into the same stream — and would interleave into your reply as gibberish. So the top-level model is tagged and only its tokens stream. That filter looks decorative. It is load-bearing.

Part 7 — The constraint that designed the system

Everything is deleted after 48 hours

The obvious part is the sweep. The non-obvious part is ordering:

Delete the SQLite row first and you lose the remote_path and chunk_count needed to clean up Pinecone and Hugging Face — orphaning data in two external systems forever, invisibly.

The more interesting consequence: if everything is deleted, users lose their work every two days. The answer wasn't to weaken the policy — it was export/import, the whole workspace as JSON. With one non-negotiable rule: credentials are stripped on export. The file gets downloaded, emailed, committed to a repo. Everything in it is re-enterable, so the safe default is the only defensible one.

What I'd tell someone building this

Six things that generalise

01

Watch how people draw the diagram

The direction bug wasn't a coding error; it was my mental model losing to the user's. When users consistently do something "wrong", the software is wrong.

02

A field that exists but does nothing is a lie

condition_expr sat in the schema and the UI for weeks doing nothing. Either wire it up or delete it.

03

Isolate every extension point

One malformed custom tool killed an entire agent because nothing was wrapped. Anything user-defined should be able to fail without taking the system with it.

04

Silent wrongness is the enemy

The GET-drops-arguments bug threw no error, logged nothing, and produced a plausible wrong answer. Those cost far more than crashes.

05

Build the trace before you need it

Once more than one model is involved, "why did it answer that?" stops being answerable by reading code. The callback handler took an afternoon and has explained every confusing run since.

06

Decide how each failure degrades

Conditional routing fails open. A broken tool is skipped. A failed run isn't written to memory. Each one is the difference between a demo and something you'd let someone use.
